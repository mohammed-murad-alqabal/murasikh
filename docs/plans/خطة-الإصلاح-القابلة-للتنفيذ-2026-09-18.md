# خطة إصلاح مستودع مُرسِّخ

**مرتبطة بالتقرير:** `docs/تقرير-المراجعة-الشاملة-2026-09-18.md`
**النسخة المستهدفة:** بعد `37c40991cd17ad082e8353866da1f6dc8f521a7b`
**الهدف:** نقل المستودع من نسخة CI فاشلة إلى نسخة مستقرة قابلة للانتقال إلى staging، ثم إعدادها للإنتاج.

## 1. قواعد التنفيذ

ينفذ الإصلاح على دفعات صغيرة مستقلة. لا تُدمج دفعة لاحقة إذا كانت دفعة CI الأساسية فاشلة. كل بند يجب أن يملك اختباراً أو تحققاً آلياً، ولا تُعتبر الوثيقة محدثة إلا بعد مطابقة الكود الفعلي.

تُحفظ تغييرات كل مرحلة في commit منفصل، وتُستخدم Pull Request حتى يمكن الرجوع إلى آخر نقطة مستقرة. لا تُستخدم إصلاحات واسعة تلقائية مثل `ruff --unsafe-fixes` أو تحديث شامل للاعتماديات في نفس commit الذي يعالج عطل الاختبارات.

## 3. المرحلة P0 — استعادة الثقة في CI

### F-01 — إصلاح قاعدة بيانات اختبارات Backend

**المشكلة المرتبطة:** R-001 وR-003.
**المالك المقترح:** Backend/QA.
**الاعتماديات:** لا يوجد.

**الإجراء:**

1. عدّل `backend/tests/conftest.py` ليستخدم `settings.SQLALCHEMY_DATABASE_URI` أو دالة موحدة تبني URI من `POSTGRES_*`.
2. أزل fallback الصامت إلى `sqlite:///:memory:` من اختبارات التكامل.
3. أضف فحصاً مبكراً يوضح أن dialect هو PostgreSQL، أو اسمح بـSQLite فقط عبر متغير صريح مثل `TEST_DATABASE_URL`.
4. اجعل workflow يمرر `TEST_DATABASE_URL` صراحةً، أو اجعل fixture يستهلك نفس Settings دون متغير ثانٍ.
5. استخدم قاعدة CI جديدة في كل تشغيل، ثم شغّل Alembic قبل pytest كما هو قائم.

**التحقق:**

```bash
cd backend
POSTGRES_SERVER=localhost POSTGRES_PORT=5433 \
POSTGRES_USER=murassikh POSTGRES_PASSWORD=murassikh_pwd \
POSTGRES_DB=murassikh_db ENVIRONMENT=testing \
SECRET_KEY=test-secret-key-for-ci-32-bytes-long \
python -m pytest -m 'not performance'
```

**معيار الإغلاق:** لا يظهر SQLite في سجل الاختبارات، وتنجح كل اختبارات Backend في GitHub Actions.

### F-02 — إصلاح اختبار debounce وسياسة الوقت

**المشكلة المرتبطة:** R-002.
**المالك المقترح:** Flutter/QA.
**الاعتماديات:** لا يوجد.

**الإجراء:**

1. احسم العقد: هل الدقيقة الواحدة مسموحة عند الوصول إليها، أم أن فترة الحظر تشمل نقطة الدقيقة؟
2. إذا كان المقصود فترة حظر شاملة، غيّر المقارنة في `HomeContextPolicy.shouldNotify` إلى `<=`.
3. إذا كان المقصود السماح بالتحديث عند الدقيقة تماماً، عدّل الاختبار إلى 59 ثانية وغيّر اسم الاختبار ليعكس ذلك.
4. أضف اختباراً لنقطتي 59 و60 ثانية حتى لا يعود الالتباس.

**معيار الإغلاق:** ينجح الاختبار على Linux وmacOS وWindows ولا يعتمد على `DateTime.now()` غير المحقون.

### F-03 — جعل ChatScreen قابلة للاختبار دون شبكة أو مؤقتات حقيقية

**المشكلة المرتبطة:** R-002.
**المالك المقترح:** Flutter.
**الاعتماديات:** F-02 غير مطلوبة، ويمكن تنفيذها بالتوازي.

**الإجراء:**

1. استخرج واجهة `ChatStorage` لعمليات Hive، وواجهة `DelayedResponseProvider` للاستطلاع.
2. مرر dependencies اختيارية إلى `ChatScreen` أو وفر factory للاختبارات.
3. أوقف polling الدوري عندما يكون provider fake أو استخدم Clock/Timer injectable.
4. في الاختبارات استبدل `pumpAndSettle` بانتظار محدود:
   - `pumpWidget`.
   - `pump` لمدة Hive initialization محددة.
   - تنفيذ event stream.
   - `pump` لمدة animation المعروفة.
5. أضف اختباراً لـ`dispose` يثبت إلغاء المؤقت وعدم تحديث Widget بعد التخلص منه.
6. لا ترفع timeout العام للاختبار لإخفاء النشاط المستمر.

**معيار الإغلاق:** الاختبارات الأربعة لـChatScreen تمر ثلاث مرات متتالية، ولا توجد شبكة أو HTTP حقيقية في الاختبار.

### F-04 — منع تكرار فشل CI وإضافة فحوص الجودة

**المشكلة المرتبطة:** R-004.
**المالك المقترح:** DevOps/QA.
**الاعتماديات:** يفضل بعد F-01 إلى F-03.

**الإجراء:**

1. أضف إلى `.github/workflows/main.yml` خطوة `ruff check backend/app backend/tests backend/scripts`.
2. أضف `ruff format --check` بعد إنشاء إعداد مشروع ثابت.
3. شغّل Ruff على دفعات، وراجع كل تغيير آلي قبل commit.
4. اجعل GitHub Actions يشغل الاختبارات Backend وFlutter على Pull Request، لا على push فقط.
5. أضف تحققاً من روابط Markdown الداخلية الأساسية.

**معيار الإغلاق:** لا توجد مخالفات Ruff، وكل وظائف CI ناجحة على Pull Request وmain.

## 4. المرحلة P1 — تثبيت العقود والأمن والسلوك

### F-05 — توحيد عقد `user_context`

**المشكلة المرتبطة:** R-012.
**المالك المقترح:** Backend/API.

**الإجراء:**

1. أنشئ نموذج Pydantic مشتركاً للحقول المسموحة: `age`, `gender`, `facial_emotion`, `biometric_stress`, ومصدر الإشارة.
2. ضع حدوداً للعمر والقيم النصية والحجم الأقصى للقاموس.
3. استخدم النموذج نفسه في النص والصوت والصفحة الرئيسية.
4. ارفض list أو scalar في `audio.user_context` برسالة 400/422، لا 500.
5. أضف اختبارات للقيم الزائدة وJSON المشوه والحقول غير المسموحة.

**معيار الإغلاق:** كل مسارات API تعيد 422 أو 400 للمدخلات غير الصالحة ولا تُلصق حقولاً غير موثوقة في الاستعلام.

### F-06 — تثبيت سياسة القرآن فقط

**المشكلة المرتبطة:** R-010 وR-005.
**المالك المقترح:** Backend/المحتوى الشرعي.

**الإجراء:**

1. عرّف `ContentPolicy.QURAN_ONLY` أو ثابتاً مشتركاً.
2. احذف السماح بالأحاديث من prompts والقوالب المستخدمة في MVP إذا كان القرار النهائي قرآنياً فقط.
3. راجع `tiered_response.py` وRAG وaudio وhome وdelayed responses تحت السياسة نفسها.
4. أضف اختباراً يرفض metadata أو response source من نوع hadith.
5. حدّث README ووثائق المحتوى بحيث تفرق بين ملفات الحديث المضمنة ومجموعة Chroma المستخدمة فعلياً.

**معيار الإغلاق:** لا يعرض أي مسار MVP حديثاً أو مصدراً غير قرآني، وتظهر السياسة في اختبار واحد على الأقل لكل مسار إخراج.

### F-07 — تقوية refresh tokens

**المشكلة المرتبطة:** R-013.
**المالك المقترح:** Backend/Security.

**الإجراء:**

1. أضف `jti` ونوع token ووقت الإصدار والانتهاء إلى claims.
2. خزّن hash لجلسات refresh في قاعدة البيانات أو مخزن مركزي.
3. طبّق rotation وإبطال token السابق بعد refresh.
4. أضف logout وإبطال كل الجلسات عند تغيير كلمة المرور أو حذف الحساب.
5. اختبر reuse detection وانتهاء الصلاحية وحذف المستخدم.

**معيار الإغلاق:** لا يستطيع refresh token القديم إصدار زوج جديد بعد تدويره، وكل جلسة يمكن إبطالها server-side.

### F-08 — جعل Rate Limiting مركزياً

**المشكلة المرتبطة:** R-008.
**المالك المقترح:** DevOps/Backend.
**الاعتماديات:** Redis في الإنتاج.

**الإجراء:**

1. مرر storage URI لـSlowAPI عبر متغير بيئة، مثل Redis داخلي.
2. لا تعتمد على `get_remote_address` وحدها عند وجود Nginx؛ عرّف سياسة trusted proxy.
3. اختبر الحدود من خلال Reverse Proxy ومن عدة workers.
4. أضف health/readiness لفشل Redis إذا كان شرطاً لتطبيق السياسة، أو حدد fallback آمناً ومعلناً.

**معيار الإغلاق:** طلبات من نفس العميل تتشارك العداد عبر workers، ولا يمكن تجاوز الحد بتغيير process.

### F-09 — تثبيت رفع الصوت

**المشكلة المرتبطة:** R-011.
**المالك المقترح:** Backend/Security.

**الإجراء:**

1. افحص magic bytes وامتداد الملف معاً.
2. افحص مدة الصوت ومعدل العينة قبل التحليل.
3. استخدم ملفاً مؤقتاً مضبوط الصلاحيات إن احتاجت المكتبة ذلك، واحذفه في `finally`.
4. اختبر ملفاً فارغاً، تالِفاً، متنکراً، شديد المدة، ومضغوطاً بشكل غير طبيعي.

**معيار الإغلاق:** كل ملف غير صالح يرفض برسالة 4xx دون استثناء 500 أو استهلاك غير محدود.

### F-10 — اختبار ترقية قواعد البيانات

**المشكلة المرتبطة:** R-015.
**المالك المقترح:** Backend/DevOps.

**الإجراء:**

1. أنشئ snapshots صغيرة لأهم إصدارات Alembic السابقة.
2. شغّل `upgrade head` من كل snapshot.
3. افحص الجداول والأعمدة والفهارس والعلاقات بعد الترقية.
4. اختبر backup/restore لقاعدة staging قبل وبعد الترحيل.
5. وثق بوضوح إن كان downgrade غير مدعوم.

**معيار الإغلاق:** لا توجد ترقية ناجحة ظاهرياً مع schema ناقص، وتوجد نتيجة استعادة موثقة.

### F-13 — تهيئة Chroma في staging والإنتاج

**المشكلة المرتبطة:** R-007.

**الإجراء:**

1. أضف خطوة release واضحة لبناء/تحميل فهرس القرآن.
2. نفذ `seed_quran.py --verify` قبل جعل Backend ready.
3. افشل الإقلاع عند اختلاف العدد أو IDs أو نوع metadata.

**معيار الإغلاق:** تشغيل staging من volumes فارغة ينتج فهرساً صحيحاً أو يفشل برسالة واضحة قبل استقبال الطلبات.

### F-14 — تقليص الاعتماديات وبناء صورة CPU قابلة للتكرار

**المشكلة المرتبطة:** R-016.

**الإجراء:**

1. استخرج requirements runtime فقط من imports ومسارات التشغيل.
2. انقل أدوات benchmark والبناء إلى ملف منفصل.
3. افصل اعتماديات GPU عن صورة CPU أو استخدم extras.
4. أضف `.dockerignore` يستبعد caches والبيانات المؤقتة وملفات الاختبار غير اللازمة للصورة.
5. قس حجم الصورة وزمن البناء قبل وبعد.

**معيار الإغلاق:** صورة الإنتاج تبني في بيئة نظيفة دون CUDA غير ضروري، مع تقرير حجم وزمن بناء.

### F-15 — ترحيل المكتبات deprecated

**المشكلة المرتبطة:** R-009 وR-017.

**الإجراء:**

- ترحيل `google.generativeai` إلى `google.genai`.
- استبدال `datetime.utcnow()` بكائنات UTC واعية بالمنطقة الزمنية.
- استبدال Pydantic `class Config` بـ`ConfigDict`.
- مراجعة Passlib/bcrypt بعد تثبيت سياسة hashing مدعومة.

**معيار الإغلاق:** لا توجد تحذيرات deprecated في CI إلا تحذيرات طرف ثالث موثقة ومقبولة.

## 6. المرحلة P3 — جاهزية الإنتاج

### F-16 — إعداد staging فعلي

1. خادم أو Cloud Run حقيقي.
2. DNS وشهادة TLS.

### F-17 — النسخ الاحتياطي والمراقبة

2. تشفير النسخ وتحديد retention.
3. اختبار restore دوري.
4. مراقبة uptime وHealthcheck.

1. Android فعلي: القفل، الإشعارات، الصوت، Health permissions.
2. iOS فعلي: Face ID/Touch ID، الإشعارات، HealthKit، background lifecycle.

4. TestFlight وInternal App Sharing.
5. أصول المتاجر وسياسة الخصوصية وشروط الاستخدام.

**معيار الإغلاق العام:** تقرير قبول يحتوي نتائج كل جهاز ونظام وإصدار، مع روابط artifacts موقعة ونتيجة smoke test إنتاجي.

## 8. بوابات القبول

### بوابة A — CI

لا تنتقل الخطة إلى P1 حتى ينجح Backend وFlutter في نفس commit. يجب أن يكون عدد الاختبارات الفاشلة صفراً، وأن ينجح Ruff و`pip-audit` وAlembic وفحص بيانات القرآن.

### بوابة B — API والأمن

لا تنتقل إلى staging حتى تمر اختبارات المصادقة، refresh rotation، العزل، Rate Limiting المركزي، رفض المدخلات غير الصالحة، ورفع الملفات التالف.

### بوابة C — التشغيل

لا يُعلن release candidate حتى ينجح نشر staging من volumes فارغة، ويُتحقق من Chroma، TLS، CORS، health/readiness، backup/restore، والمراقبة.

### بوابة D — الأجهزة والمتاجر

لا يُعلن إطلاق عام حتى تنجح مصفوفة Android وiOS، ويُبنى الإصدار الموقّع وتُراجع مواد المتاجر والخصوصية والتراخيص.
