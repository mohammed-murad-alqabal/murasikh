# خطة الإصلاح القابلة للتنفيذ لمشروع مُرَسِّخ

**مرتبطة بالتقرير:** `docs/reports/تقرير-المراجعة-الشاملة-2026-09-20.md`  
**النسخة المرجعية:** `a9974ebb3b8d947e402ac48aa841d909d5ca43bd`  
**الهدف:** نقل المشروع من حالة CI أخضر إلى إطلاق إنتاجي آمن وقابل للاستعادة.

## قواعد التنفيذ

1. لا يُنشر الإصدار العام قبل إغلاق جميع بنود P0 واجتياز بوابة staging.
2. كل تغيير يرافقه اختبار فشل واختبار نجاح، وتحديث وثيقة العقد أو التشغيل عند الحاجة.
3. لا تُستخدم بيانات أو أسرار الإنتاج في CI أو بيئة التطوير.
4. كل مرحلة تنتهي بـcommit صغير قابل للمراجعة، ثم CI كامل على PostgreSQL حقيقي.

## المرحلة 1 — إغلاق عوائق P0

### 1.1 إصلاح Chroma والنشر الجديد — F-01

**التنفيذ:**

1. فصل `seed_quran.py --verify` عن `init_chroma`؛ أضف أمر init idempotent ينشئ المجموعة ويعيد بناء الفهرس من artifact معروف.
2. اجعل Compose يستخدم خدمة `chroma-init` لمرة واحدة، ويتوقف Backend حتى تنجح.
3. أضف version marker وعدد السجلات وchecksum؛ ارفض فهرساً ناقصاً أو بإصدار غير متوافق.
4. لا تضع Chroma DB الناتج في Git؛ استخدم volume أو artifact موثقاً.
5. اختبر deploy من volumes فارغة، وrestart، وإعادة تشغيل init مرتين.

**معيار الإغلاق:** `docker compose -f docker-compose.production.yml up` ينجح من volumes فارغة، و`/ready` لا يصبح أخضر قبل اكتمال الفهرس.

### 1.2 إغلاق cleartext في Android — F-02

**التنفيذ:**

1. أزل `usesCleartextTraffic="true"` من release manifest.
2. أنشئ Network Security Config للـdebug فقط يسمح localhost/LAN عند الحاجة.
3. افصل `API_BASE_URL` بين debug وrelease؛ لا تستخدم عنوان LAN افتراضياً في release.
4. أضف فحص CI يفشل إذا احتوى release manifest على cleartext أو `http://`.

**معيار الإغلاق:** `flutter build apk --release` يمر، وفحص APK/manifest يثبت HTTPS فقط.

### 1.3 نقل JWT إلى secure storage وإضافة refresh flow — F-03

**التنفيذ:**

1. استخدم `flutter_secure_storage` لـaccess وrefresh tokens.
2. عدّل AuthService لحفظ token pair وإزالتهما معاً.
3. أضف interceptor في ApiService: عند 401 ينفذ refresh مرة واحدة، يعيد الطلب الأصلي، ويمنع race عبر mutex.
4. عند فشل refresh نفذ logout محلياً واطلب `/auth/logout` إن أمكن.
5. لا تسجل tokens أو Authorization headers في logs.

**اختبارات:** تخزين آمن، 401 ثم refresh، refresh متزامن، refresh منتهي، logout، وعدم تسريب القيمة في logs.

**معيار الإغلاق:** لا يوجد token في SharedPreferences، وكل اختبارات Auth وAPI تعمل على جهاز/محاكي.

### 1.4 ضمان المسح المحلي — F-04

**التنفيذ:**

1. اجعل `clearAllUserData()` يمسح Hive/cache/history المحليين في `finally` أو مسار مستقل.
2. افصل نتيجة `localCleared` عن `remoteDeletionConfirmed`.
3. عند فشل الخادم خزّن pending deletion بدون بيانات حساسة، أو اعرض للمستخدم أن الحذف البعيد لم يُؤكّد.
4. امنع إعادة مزامنة البيانات المحذوفة من طابور offline.

**اختبارات:** نجاح الشبكة، انقطاع الشبكة، 500، timeout، restart بعد المسح، وعدم بقاء أي سجل محلي.

**معيار الإغلاق:** طلب المسح يزيل البيانات المحلية حتى مع خادم متوقف ولا يعلن اكتمال الحذف البعيد كذباً.

## المرحلة 2 — موثوقية التشغيل وسلامة العقود

### 2.1 Redis وtrusted proxy — F-05

- مرّر `REDIS_URL` من `.env.production` إلى Backend، واسمح بالفشل الآمن إذا تعذر Redis.
- اجعل rate limiting موزعاً عبر Redis، مع namespace وإعداد TTL واضح.
- لا تقبل `X-Forwarded-For` إلا من شبكة Nginx أو proxy موثوق محدد.
- امنع الوصول الخارجي المباشر إلى Backend وRedis وPostgreSQL.
- أضف اختبارات multi-worker، restart، وRedis unavailable.

**القبول:** الطلبات من نسختين تشترك في limit واحد، وIP المزور لا يغير الهوية.

### 2.2 تشديد API schemas — F-06

- قيّد rating إلى المجال الموثق.
- قيّد confidence إلى `0.0..1.0`.
- استخدم `Literal` أو enums لـ`signal_source` و`time_of_day`.
- ضع حدود طول وتطبيعاً لحقول التسجيل والرسائل.
- وحّد schema بين recommend وaudio وhome، ووثق status codes.
- أضف اختبارات 422 للحقول السالبة، الزائدة، الطويلة، والأنواع الخاطئة.

### 2.3 جعل refresh والتسليم ذريين — F-07

- نفّذ refresh rotation بتحديث مشروط: `UPDATE ... WHERE refresh_jti = old_jti` ثم تحقق من row count.
- أضف unique/index مناسباً لـ`refresh_jti`.
- اجعل تسليم delayed responses claim ذرياً باستخدام row lock أو `SKIP LOCKED`.
- أضف idempotency key أو delivery marker يمنع الإرسال المزدوج.
- اختبر 10 طلبات refresh متزامنة و10 workers للردود المؤجلة.

**القبول:** طلب واحد فقط ينجح بالـrefresh القديم، وكل رد مؤجل يسلم مرة واحدة.

### 2.4 حماية النص القرآني — F-08

- افصل `verse_text` الأصلي عن `explanation` المولّد.
- لا تسمح للنموذج بإعادة كتابة الآية؛ أعد النص من Chroma/المصدر الموثوق.
- تحقق من verse id وsurah/ayah قبل الإرسال.
- أضف اختباراً يحقن prompt يطلب تغيير النص ويتأكد أن الاستجابة تحافظ على الأصل.

### 2.5 إزالة حجب Event Loop — F-09

- حمّل النموذج عند startup خارج مسار الطلب، أو استخدم `asyncio.to_thread` مع lock.
- ضع timeout وcircuit breaker للفallback المحلي.
- قس زمن أول طلب والطلبات اللاحقة.
- أضف اختباراً يثبت أن endpoint آخر يستجيب أثناء التحميل.

### 2.6 liveness وreadiness — F-10

- أبقِ `/health/live` خفيفاً ولا يفحص اعتماديات خارجية.
- أضف `/health/ready` يفحص PostgreSQL وRedis وChroma بمهلة قصيرة.
- اجعل Docker وNginx وorchestrator يستخدمون readiness.
- لا تُرجع أسراراً أو connection strings في الرد.
- أضف اختبارات حالة كل dependency وحالة timeout.

## المرحلة 3 — الاستمرارية وCI/CD الإنتاجي

### 3.1 backup/restore — F-11

1. حدد RPO وRTO لكل PostgreSQL وChroma والملفات المرفوعة.
2. أنشئ backup مشفراً، مضغوطاً، وموقعاً أو قابلاً للتحقق من integrity.
3. ارفع النسخ إلى تخزين خارجي مع retention وrotation؛ لا تحفظها على نفس host فقط.
4. أضف جدولة موثقة وتنبيهاً عند الفشل.
5. نفذ restore drill أسبوعي على بيئة معزولة، وسجل زمن الاستعادة وchecksum.
6. وثق إجراء rollback وincident response.

**القبول:** استعادة نسخة فعلية على host منفصل وتشغيل API وChroma منها بنجاح.

### 3.2 بوابات CI/CD — F-12

- تحقق من YAML وShell وCompose.
- ابنِ images الإنتاجية مع pinned digest وفحص CVE.
- شغّل Compose من volumes فارغة في CI.
- اختبر Nginx config وTLS headers وhealth checks.
- أضف coverage threshold وmigration upgrade/downgrade حيثما كان آمناً.
- ابنِ Android release وiOS archive في بيئة أسرار محمية عند توفر runner.
- لا تنشر إلا من tag موافق عليه وبعد نجاح staging smoke test.

## سجل التنفيذ — 2026-09-21

تم تنفيذ دفعة P0/P1 في المستودع، وتشمل تهيئة Chroma ذات الإصدار والبصمة مع volume مستقل في Compose، وإضافة readiness يفحص PostgreSQL وRedis وChroma، وتمرير `REDIS_URL`، وتقييد trusted proxy، وتشديد عقود Home وconfidence، وتدوير refresh token بتحديث ذري، ومنع التسليم المزدوج للردود المؤجلة، وتركيب نص الآية من المصدر بدلاً من مخرجات النموذج، وضمان مسح البيانات المحلية عند فشل الحذف البعيد، وإزالة جلب widget غير الآمن، وإضافة اختبارات لهذه المسارات.

الفحوص المحلية المنجزة لهذه الدفعة هي Ruff، وcompileall، وbash syntax، و12 اختبار Backend مستهدفاً. ما يزال إغلاق بوابات الإصدار مشروطاً بنجاح CI البعيد، وتشغيل Flutter الفعلي بعد تحديث `pubspec.yaml`، واختبار Compose من volumes فارغة، وrestore drill فعلي، واختبارات الأجهزة والمتاجر. لذلك لا تُوسم بوابة P0 أو staging كمكتملة قبل ظهور الأدلة التشغيلية المذكورة.
