## الحكم التنفيذي

المستودع في حالة جيدة من ناحية الدمج واختبارات CI الحالية، لكنه **غير جاهز لإطلاق إنتاجي رسمي**. آخر CI نجح في Ruff، و`pip-audit --strict`، وترحيلات Alembic، وفحص بيانات القرآن، و68 اختبار Backend، و4 اختبارات أداء، وFlutter analyze، واختبارات Flutter. الفرع الرئيسي نظيف ولا توجد Pull Requests مفتوحة.

لكن توجد أربع عوائق P0 يجب إغلاقها قبل الإصدار: تهيئة Chroma عند النشر الجديد، السماح بالاتصالات غير المشفرة في Android، تخزين JWT في `SharedPreferences` مع غياب refresh flow في العميل، ومسح البيانات المحلية عند فشل الحذف البعيد. توجد بعد ذلك فجوات P1 في readiness وRedis وسلامة RAG والنسخ الاحتياطي وCI الإنتاجي، وفجوات P2 في التوثيق والتغطية وبناء المتاجر.

**قرار الإصدار:** مواصلة التطوير والدمج مسموحان؛ النشر العام مرفوض حتى إغلاق P0 ثم اجتياز staging نظيف.

## النتائج التفصيلية

### F-01 — Chroma قد يمنع الإقلاع — P0

يبدأ `docker-compose.production.yml` Backend بالأمر `python scripts/seed_quran.py --verify`. هذا الخيار يتحقق فقط من وجود مجموعة Chroma التي تحتوي 6,236 آية؛ ولا ينشئ الفهرس. وفي المقابل `backend/chroma_db/` غير متعقب في Git ومذكور في `.gitignore`. لذلك قد يفشل نشر جديد أو volume فارغ في restart loop.

**الإصلاح المطلوب:** init job أو artifact/versioned seed process، مع اختبار نشر من volumes فارغة. لا ينبغي اعتماد volume محلي لجهاز المطور.

### F-02 — Android يسمح بالـcleartext — P0

يحتوي `frontend/android/app/src/main/AndroidManifest.xml` على `android:usesCleartextTraffic="true"`. هذا يتعارض مع إعلان HTTPS الإجباري ويزيد احتمال تسريب JWT وبيانات المستخدم عند سوء ضبط عنوان API.

**الإصلاح المطلوب:** تعطيل cleartext في release، والسماح به في debug فقط عبر Network Security Config، وإضافة فحص build يمنع الإعداد في release.

### F-03 — JWT في Flutter غير محمي ولا يوجد refresh flow — P0

يحفظ `AuthService` `jwt_token` في `SharedPreferences` ولا يحفظ `refresh_token`. وعند 401 تقوم `ApiService` بتسجيل الخروج بدلاً من تجديد access token وإعادة الطلب مرة واحدة. بذلك لا يستفيد العميل من refresh rotation الموجود في Backend، ويبقى access token في تخزين غير مخصص للأسرار.

**الإصلاح المطلوب:** secure storage، interceptor للتجديد مع قفل يمنع refresh المتزامن، ثم logout وإبطال refresh token عند الفشل.

### F-04 — مسح الخصوصية لا يمسح المحلي عند فشل البعيد — P0

`PrivacyDataService.clearAllUserData()` يفشل مبكراً عندما تفشل `HistoryService.clearHistory()` أو لا يتوفر الخادم، وقد لا يمسح Hive chat/history/cache رغم طلب المستخدم.

**الإصلاح المطلوب:** مسح المحلي فوراً وبشكل مستقل، ثم محاولة الحذف البعيد مع pending deletion أو نتيجة صريحة لا تدعي اكتمال الحذف البعيد.

### F-05 — Redis وموثوقية عنوان العميل — P1

يوجد Redis في Compose، لكن Backend لا يتلقى `REDIS_URL` في إعداد الإنتاج؛ فيعود rate limiting إلى storage محلي غير مناسب لعدة نسخ أو لإعادة التشغيل. كما أن أول قيمة من `X-Forwarded-For` تؤخذ دون trusted proxy، ما يسمح بتزوير IP عند الوصول المباشر.

**الإصلاح المطلوب:** تمرير Redis صراحة، اختبار فشل Redis، قصر الوصول على Nginx، وإعادة بناء headers من proxy موثوق فقط.

### F-06 — عقود API غير مقيدة بما يكفي — P1

`AppRatingRequest.rating` بلا range، و`ContextSignalsRequest.confidence` بلا 0–1، و`signal_source` و`time_of_day` غير مقيدين، كما أن confidence في response غير مقيد. نماذج التسجيل لا تفرض حدوداً كافية للطول والبريد.

**الإصلاح المطلوب:** `Field` و`Literal` وقيود range، واختبارات 422 للحالات الخارجة عن العقد.

### F-07 — سباقات refresh والردود المؤجلة — P1

قراءة `refresh_jti` ثم تحديثه ليست compare-and-swap ذرية، وقد ينجح طلبان متزامنان. كذلك يقرأ `deliver_due()` السجلات ثم يعلّمها قبل commit، ما يسمح بتسليم مزدوج.

**الإصلاح المطلوب:** update ذري مشروط أو قفل صف للـrefresh، و`FOR UPDATE SKIP LOCKED` أو claim/idempotency للردود المؤجلة، مع اختبارات concurrency.

### F-08 — سلامة النص القرآني تعتمد على prompt — P1

يمرر RAG الآية إلى Gemini ويعيد النص الناتج دون مقارنة آلية بالنص الأصلي.

**الإصلاح المطلوب:** أن يركّب التطبيق الآية الأصلية بنفسه، ويستخدم Gemini للشرح فقط، مع اختبار يمنع تغيير النص أو المصدر.

### F-09 — تحميل النموذج يحجب Event Loop — P1

يستدعي `RAGEngine.format_response()` تحميل النموذج المحلي بشكل متزامن داخل دالة async.

**الإصلاح المطلوب:** startup task أو `asyncio.to_thread` مع lock، أو استبعاد fallback من صورة الإنتاج إذا لم يكن مطلوباً.

### F-10 — health ليس readiness — P1

`/health` يفحص حالة العملية فقط ولا يفحص PostgreSQL أو Redis أو Chroma، بينما توثق الملفات live/ready endpoints غير موجودة.

**الإصلاح المطلوب:** فصل liveness عن readiness بمهلات قصيرة وردود آمنة تفحص الاعتماديات الضرورية.

### F-11 — النسخ الاحتياطي غير مثبت تشغيلياً — P1

`deploy/backup.sh` و`deploy/restore.sh` موجودان، لكن لا توجد جدولة أو نسخة خارجية مشفرة أو restore drill آلي. وثيقة الأمان تعلن AES-256، بينما السكريبت يضغط SQL فقط.

**الإصلاح المطلوب:** تحديد RPO/RTO، تشفير ورفع النسخ، تدوير المفاتيح، واختبار استعادة دوري على قاعدة منفصلة.

### F-12 — CI لا يثبت قابلية production — P1

لا يبني CI Compose الإنتاجي، ولا يختبر volumes فارغة، ولا يفحص Nginx/TLS أو images، ولا يبني Android/iOS release، ولا يفرض coverage threshold أو downgrade للترحيلات.

**الإصلاح المطلوب:** إضافة pipeline إنتاجي مستقل وبوابات staging وبناء موقّع وفحص صور.

### F-13 إلى F-16 — ملاحظات إضافية — P2/P3

`backend/requirements.txt` يحتوي 154 إصداراً مختلطاً بين direct وtransitive، ويضم SDKs غير مستخدمة ظاهرياً. الاختبارات لا تغطي secure storage وoffline deletion وrefresh concurrency وreadiness وbackup/restore وCompose من volume فارغ وcleartext في Android. كما وجد فحص الروابط ثلاثة روابط مكسورة إلى `plans/todo-1.md` بينما الملف الفعلي `todo_1.md`. دليل النشر يستخدم `docker-compose.prod.yml` و`seed_data.py`، بينما الملفات الفعلية تستخدم `docker-compose.production.yml` و`seed_quran.py`. وثيقة الأمان تعلن HS256 و30 دقيقة وCSP وAES-256 بما لا يطابق التنفيذ. وأخيراً لا يثبت وجود build موقّع أو اختبار أجهزة/متاجر.

## نقاط القوة

يوجد Alembic متسلسل، schemas مشتركة، تحقق magic bytes للصوت، حد رفع، عزل مستخدم في السجل، refresh JTI أساسي، fallback محلي، وCI يستخدم PostgreSQL حقيقياً ويشغل Ruff وpip-audit وفحص البيانات. كما يفرض سكريبت القرآن العدد والهوية ونوع السجلات.

## حدود المراجعة

لم تشمل المراجعة اختبار اختراق خارجي، أو مراجعة قانونية لمصادر البيانات، أو تجربة جهاز Android/iOS حقيقي، أو نشر staging فعلياً. هذه بوابات لاحقة وليست ناجحة بمجرد الفحص الثابت.
