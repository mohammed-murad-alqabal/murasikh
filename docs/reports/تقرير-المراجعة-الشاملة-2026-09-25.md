## Executive Summary

Murasikh هو **MVP تجريبي/مشروط للـstaging**، وليس منتجاً Production Ready أو Verified end-to-end. النواة الموجودة فعلاً هي رحلة نصية من إدخال المستخدم إلى تحليل أولي، واسترجاع آية من قاعدة Quran-only عبر Chroma، وصياغة رد، وحفظ التفاعل للمستخدم المصادق، مع Home سياقي، مصادقة، سجل، تقييم، وتحليل صوتي/وجه تجريبي. الأدلة الرئيسية هي `README.md:20-37,170-175`، تسجيل المسارات في `backend/app/main.py:28-34`، عقد API في `docs/03-api/العقد-المعتمد.md:28-118`، ومسار التوصية في `backend/app/api/v1/endpoints/recommend.py:57-305`.

**ما يعمل أو له تنفيذ واضح:**

- المسار القانوني الأساسي هو `POST /api/v1/analyze`، مع Home عبر `GET /api/v1/home/verse`؛ واختبار route contract يحرس المسارات القديمة (`backend/tests/test_api/test_route_contract.py:5-33`).
- سياسة Quran-only موجودة ومفروضة جزئياً في seed والـfilters، مع تحقق من 6236 آية واختبارات منع الحديث (`backend/tests/test_services/test_seed_quran.py:67-107` و`test_no_hadiths.py`).
- المصادقة تستخدم Argon2id، وJWT access/refresh مع تدوير refresh JTI، وعزل سجل المستخدم في المسارات الأساسية (`backend/app/services/user_manager.py:10-25`، `backend/app/core/auth.py:14-62`، `test_user_isolation.py`).
- لدى Flutter cache وfallback وطابور feedback محلي، ولدى backend queue للردود المؤجلة وhealth/readiness وCompose ونسخ احتياطي أولي.
- توجد اختبارات مصدرية وworkflow CI، لكنها ليست دليلاً بذاتها على نجاح التشغيل أو صحة الإنتاج.

**ما يمنع اعتماد الجاهزية:**

1. فجوة جوهرية بين رؤية المنتج الواسعة (الصوت، الصورة، القرآن والسنة) وبين النطاق التشغيلي الحالي (توصية قرآنية نصية، مع صوت ووجه تجريبيين؛ الحديث خارج العقد).
2. لا توجد أدلة تشغيل محفوظة لـ`pytest` أو Flutter أو Docker أو staging أو جهاز أو signed artifact؛ في بيئة المراجعة كان `pytest` و`flutter` و`docker` غير متاحة، ونجح `compileall` فقط.
3. حذف الحساب غير منفذ كحذف شامل؛ الموجود يحذف التاريخ فقط، بينما السياسة تعد بحق أوسع (`PRIVACY_POLICY.md:21-24` مقابل `history.py:34-44`).
4. logout يبطل refresh فقط، ولا يبطل access token الحالي حتى انتهاء صلاحيته (`auth.py:170-178`، `core/auth.py:52-62`).
5. fallback العميل يحول أخطاء 401/422/500 وtimeouts إلى توصية offline في حالات واسعة، ما قد يعرض نتيجة قديمة كأنها تحليل ناجح (`frontend/lib/services/api_service.dart:119-139`).
6. smoke والوثائق والعقد غير متزامنة: smoke يستدعي `/api/v1/analyze/recommend` بينما المسار الفعلي `/api/v1/analyze`، ووثيقة المصادقة تصف JSON/email و`/auth/me` بينما التنفيذ يستخدم OAuth2 form ولا ينفذ `/me`.
7. queue الرد المؤجل at-most-once، وfeedback offline غير idempotent؛ قد تفقد الرسالة أو تتكرر التقييمات.
8. provenance القرآني وتقييم الملاءمة العربية غير مثبتين؛ integrity البنيوية لا تساوي جودة دلالية أو سلامة شرعية.
9. النسخ الاحتياطية مضغوطة ومتحقق من checksum فقط، غير مشفرة، ومسارات backup/restore متعارضة ولا يوجد restore drill أو RPO/RTO مثبت.
10. لا توجد observability/SLO/alerts أو pipeline نشر وترقية وrollback؛ CI الحالي validation pipeline فقط.

**الحكم التنفيذي:** اعتماد المشروع كـ**MVP تجريبي؛ Staging مشروط**. النواة النصية Quran-only يمكن مواصلة تثبيتها، لكن لا يجوز إعلان المنتج Production Ready أو Verified أو الادعاء بفهم نفسي/متعدد الوسائط/عمل كامل دون اتصال أو حذف شامل قبل إغلاق بوابات السلامة والتكامل والخصوصية والتشغيل أدناه.

## Core User Journey Audit

### الرحلة المتوقعة

1. فتح التطبيق وتهيئة Hive والخدمات (`frontend/lib/main.dart:66-168`).
2. التنقل إلى Home أو Chat (`main_shell.dart:22-68`).
3. إدخال نص وبناء `user_context` و`chat_history` (`chat_screen.dart:277-305`).
4. استدعاء `POST /api/v1/analyze` (`api_service.dart:200-229`).
5. تحليل الرسالة في `conversational_agent.py`، ثم Chroma/RAG، ثم تركيب الرد في `recommend.py` و`rag_engine.py`.
6. حفظ Interaction للمستخدم المصادق، وعرض الرد والمصدر والتفسير.
7. feedback، history، وdelayed response عند انطباق الشروط.

### ما ثبت مصدرّياً

- العميل والـbackend يتفقان على `/analyze` وحقول النص والسياق الرئيسية.
- model Flutter يتعامل مع `message`, `source`, `tafsir`, `interaction_id`, و`delayed_message`.
- وجود state loading/loaded/error واختبارات Chat/offline.

### نقاط الانقطاع أو التضليل

- `scripts/smoke_test.sh:26-29` يستدعي `/api/v1/analyze/recommend`، وهو غير مسجل؛ المسار الفعلي `/api/v1/analyze`.
- أي exception واسع في `ApiService` قد يعود بـoffline recommendation؛ 401 أو 500 قد يظهران للمستخدم كإجابة قديمة.
- `clearChat` في `chat_screen.dart:188-221` يستدعي `DELETE /api/v1/history`، فيمسح كل تاريخ الحساب لا المحادثة الحالية.
- `RecommendationScreen` تعرض thumbs وتغيير Snackbar فقط (`recommendation_screen.dart:274-340`) دون إرسال feedback، بينما المسار المستخدم في MainShell هو ChatScreen.
- المصادقة ليست auth gate مركزياً؛ AuthScreen تصل أساساً من Settings، فلا يوجد session state واضح في MainShell.
- history المحلي والبعيد يندمجان دون protocol صريح للحذف أو رفع السجلات المحلية بعد login.

**حكم الرحلة:** المسار النصي موجود ومتماسك على مستوى المصدر، لكنه **Partially Implemented وغير Verified عابراً للحدود**. لا يجوز اعتبار fallback نجاحاً خادمياً أو اعتبار clear chat حذفاً آمناً قبل فصل الحالات والعقود.

## Architecture Assessment

### نقاط القوة

- فصل معقول بين FastAPI endpoints، خدمات AI/RAG، repositories، Flutter services، وواجهات العرض.
- مسارات قانونية محددة تحت `/api/v1` واختبار route contract يمنع المسارات القديمة.
- PostgreSQL للتاريخ والردود المؤجلة، وChroma لمصدر التوصية، وsecure storage للتوكنات.
- Compose يحدد Postgres/Redis/Chroma/Nginx مع healthchecks ومنافذ عامة محدودة (`docker-compose.production.yml`).

### الديون المعمارية

1. **مصادر حقيقة متعددة:** كود FastAPI، `العقد-المعتمد.md`، وثائق عامة وقاموس البيانات، Flutter models، وsmoke scripts تختلف في paths/fields.
2. **خلط lifecycle:** `backend/entrypoint.sh` وCompose ينفذان seed/migration عند startup ثم Uvicorn؛ لا يوجد one-shot migration job أو lock/rollback.
3. **async/sync:** handlers async تستدعي SQLAlchemy synchronous مباشرة؛ قد يحجب ذلك event loop تحت بطء DB.
4. **session والذاكرة:** authenticated يبني history من DB، guest من transcript العميل؛ لا conversation/session identity أو TTL موحد.
5. **Quran-only موزع:** filters في endpoints لا validator مركزي fail-closed؛ runtime policy أضعف من seed policy.
6. **cache غير مدمج:** `RedisCache` prototype بلا call sites واضحة أو policy لاستثناءات Redis/JSON.
7. **غياب idempotency:** retries بعد timeout قد تنشئ Interaction وdelayed response مكررين.
8. **تشعب deployment:** `docker/Dockerfile` و`backend/Dockerfile`، وCompose development/staging/production ومسارا backup، دون canonical artifact.

**القرار المعماري:** لا يوجد دليل يبرر Rewrite أو Microservices. الأولوية هي توحيد العقود، حدود المسؤوليات، وبوابات التشغيل داخل البنية الحالية؛ يمكن معالجة المخاطر بإصلاحات تطورية.

## AI/User Understanding

### الواقع

`conversational_agent.py:28-45,52-107` يطلب action وemotion وconfidence، مع fallback كلمات ثابتة. `recommend.py:102-162` يستخدم emotion لبناء semantic query، و`Interaction` يخزن detected_emotion. `UserContextSchema` (`common.py:6-18`) يحمل age/gender/facial_emotion/biometric_stress، لكنه ليس نموذجاً لـuser state.

### الحكم

النظام **لا يميز نموذجياً** بين emotion وstate وneed وintent. هذا يقلل قابلية التفسير والقياس: لا يمكن معرفة هل الآية اختيرت بسبب حاجة عملية، نية سؤال، إحالة سياقية، أم كلمة عاطفية سطحية. وجود إشارات الوجه/الضغط لا يثبت فهماً نفسياً ولا ينبغي عرضه كذلك.

### ما يجب أن يكون في التصميم المستهدف

- حقول مستقلة: `emotion`, `user_state`, `need`, `intent`، ولكل منها confidence وevidence ومصدر (`text`, `history`, `sensor`, `user-stated`).
- سياسة تعارض: ما الذي يحدث عند اختلاف النص عن heuristic الوجه؟
- golden Arabic set تشمل النفي، تعدد المشاعر، الإحالات، اللهجات، الأسئلة العملية، والنصوص الحساسة.
- privacy purpose limitation: لا ترسل age/gender/face/stress إلى مزود AI دون consent وتقليل/redaction.

## Conversation/Investigation

المنتج الحالي ليس محققاً لحالة المستخدم؛ هو **مصنف أولي + مسترجع آية**. سجل الحوار للمصادق يعتمد آخر خمس interactions، والضيف يعتمد transcript محدوداً. لا يوجد `conversation_id` أو session TTL أو canonical memory.

المخاطر:

- نفس النص قد ينتج سلوكاً مختلفاً حسب authenticated/guest، لأن مصدر التاريخ مختلف.
- backend authenticated history يضيف role=`ai`، بينما العقد الداخلي يقبل `user/assistant` (`recommend.py:68-90` مقابل `ChatHistoryMessage`).
- فرع `action=ask` لا يمرر confidence وresponse tier صراحة إلى history؛ defaults قد تسجل السؤال كتوصية moderate بثقة 1.0 (`recommend.py:102-125`، `history_manager.py:16-39`).
- لا يوجد investigation loop: سؤال استيضاح، فرضية، دليل، ثم توصية/تصحيح. لذلك يجب عدم تسويق النظام كفهم عميق أو دعم علاجي.

**الاتجاه:** ابدأ بعقد محادثة صغير وصريح: session، message، analysis، retrieval، response، feedback. احتفظ بالمحادثة مع حدود وTTL، ولا تضف “ذاكرة تعلم” قبل تعريف consent، provenance، وحذفها.

## Recommendation & Quran Retrieval

### ما يعمل

- `embeddings.py` يستخدم `paraphrase-multilingual-MiniLM-L12-v2` وChroma PersistentClient.
- `rag_engine.py:187-248` ينفذ ترشيحاً وترتيباً هجينا، و`rag_engine.py:304-343` يركب النص المسترجع/source خارج Gemini، ما يقلل إعادة كتابة الآية.
- seed يتحقق من 114 سورة و6236 آية وIDs/type/idempotency (`seed_quran.py:66-212`).
- endpoints تطلب `filters={type: verse}`، و`test_no_hadiths.py` يحرس السياسة على مستوى مصدرّي.

### ما لا يزال خطراً

1. **fallback Home غير canonical:** `home.py:59-91` يحتوي نصوصاً يدوية؛ المقارنة مع `quran.json` أثبتت اختلافات exact في النص/الضبط/نطاق الآيات.
2. **fail-open عند درجات سلبية:** `rag_engine.py:244-248` قد يعيد أعلى مرشح حتى لو كانت كل الدرجات سالبة، بما في ذلك آية وعيد.
3. **Quran-only غير invariant مركزي:** filter موزع، ولا validator يرفض result غير verse في كل caller.
4. **provenance ناقص:** `quran.json` يحتوي chapter/verse/text فقط؛ لا source version/license/hash/review status، و`source` المعروض مرجع مولد لا يثبت provenance.
5. **تعارض نموذج embedding:** ADR `docs/06-knowledge-base/adr/004-نموذج-Embedding.md` يعلن GATE-AraBERT-v1، بينما الكود يستخدم MiniLM.
6. **لا evaluation عربية:** الاختبارات الحالية orchestration/mocks/structural integrity أكثر من Recall@k أو MRR/nDCG أو faithfulness.

### البوابة المطلوبة

لا يرفع هذا المحور إلى Production Ready قبل manifest versioned للمصحف والتفسير، hash لكل record/index، exact equality tests، golden relevance set عربية، threshold يرفض المرشح غير الآمن، ونتائج CI مرتبطة بإصدار model/index/corpus.

## Memory/History

### ما يعمل

- server history مرشح بـ`user_id`، مع اختبارات عزل (`history_manager.py:48-100`, `test_user_isolation.py`).
- `Interaction` يحفظ response وfeedback، والـfrontend يدمج remote/local ويقدم cache.
- export موجود في `auth.py:130-148` ويستهلكه `privacy_data_service.dart`.

### الفجوات

- `DELETE /history` يحذف التاريخ، لكنه ليس `delete-account` ولا يمسح User أو settings أو tokens أو backups أو provider data.
- Hive يخزن JSON غير مشفر؛ namespace isolation ليس encryption (`local_account_scope.dart:5-9`, `offline_service.dart:79-84`).
- local/remote merge لا يملك tombstones أو pending upload أو سياسة server-authoritative واضحة.
- feedback queue ترسل عناصر بلا event UUID/idempotency key؛ failure/decode قد يضيع أو يعيد العناصر.
- delayed delivery تعلّم `is_delivered=True` داخل GET قبل ACK العميل (`delayed_response_service.py:47-80`).

**حكم الذاكرة:** عزل الحساب في المسارات الأساسية جيد، لكن lifecycle البيانات غير مكتمل، والحذف المعلن أوسع من التنفيذ. هذه بوابة **Critical**.

## Multimodal

### الصوت

رفع الصوت يفحص MIME وmagic bytes والحجم 10MB (`audio.py:28-76`)، وتحليل الصوت يستخرج features ويصنف tone (`audio_analyzer.py:12-73`). لكن المصنف heuristic، وexception قد يعيد `normal/confidence=0.5`، فلا يجوز اعتباره ASR أو مقياساً نفسياً. لا توجد حدود codec/مدة/جهاز أو اختبار ملف صوت فعلي عبر HTTP.

### الوجه والحساسات

`face_emotion_service.dart:111-205` يطبق heuristic محلياً، وتُمرر `facial_emotion` و`biometric_stress` إلى prompt عند وجود Gemini (`conversational_agent.py:64-83`). لا يثبت ذلك الدقة أو consent أو ضرورة البيانات. يجب جعلها opt-in، موسومة تجريبية، مع عدم إرسالها افتراضياً إلى مزود خارجي.

### Offline

التطبيق يعرض cache حسب emotion أو آخر نتيجة أو fallback ثابت (`api_service.dart:233-247`). هذا **استمرار عرض** لا تحليل محلي. يجب أن يظهر للمستخدم المصدر والعمر والحالة `offline/stale/fallback`، وألا تحفظ النتيجة كأنها معالجة خادم حديثة.

## Performance

لا توجد قياسات إنتاجية للمسار الكامل. اختبارات `backend/tests/performance` تستخدم model/store وهميين وتقيس حلقات محلية بحد p95 أقل من 20ms؛ README نفسه يذكر أنها ليست production load. لا توجد baseline لـHTTP/DB/Chroma/embedding/Gemini أو concurrency أو CPU/RAM أو pool saturation.

المخاطر التقنية:

- sync SQLAlchemy داخل handlers async.
- AI وembedding وRAG في المسار نفسه مع timeouts غير موحدة.
- Uvicorn process واحد بلا worker/resource policy في Compose.
- لا SLO لـp95/p99 أو error budget.

**المطلوب:** benchmark staging ببيانات Quran/Chroma حقيقية، حمل concurrent، قياس p50/p95/p99 وRPS والـ5xx والـtimeouts وCPU/RAM واتصالات DB، ثم ربط النتائج بـSLO؛ لا يُستنتج scale لمليون مستخدم من المتطلبات القديمة.

| مجال | الوضع | القرار |

## Security & Privacy

### نقاط قوة مثبتة مصدرّياً

- Argon2id بإعدادات معتبرة (`user_manager.py:10-25`).
- access/refresh JWT مع `exp` و`type` وتدوير refresh JTI ذري نسبياً (`core/auth.py:14-62`).
- Pydantic limits للنص والسجل، وMIME/magic/10MB للصوت.
- Nginx يفرض HTTPS/TLS 1.2+ وHSTS وtimeouts وحدود حجم (`deploy/nginx/nginx.conf:20-81`).
- tokens في `flutter_secure_storage`.

### المخاطر الحرجة

1. **حذف غير شامل:** لا `delete-account`؛ لا حذف مضمون لـUser/preferences/tokens/backups/exports/provider data. السياسة أوسع من العقد (`PRIVACY_POLICY.md`، `auth.py`، `privacy_data_service.dart`).
2. **Hive غير مشفر:** cache/chat/history/settings JSON plaintext؛ auto-lock وnamespace لا يكفيان.
3. **logout غير فوري:** access token صالح حتى 15 دقيقة (`core/config.py:32-36`).
4. **AI data governance ناقصة:** context الحساس يذهب إلى Gemini دون consent/redaction/retention (`core/config.py:25-30`).
5. **auth schema ضعيف ومتضارب مع docs:** لا min/max وEmailStr؛ email اختياري يولد هوية مصطنعة؛ الوثيقة تصف bcrypt/HS256/JSON بينما التنفيذ Argon2id/HS512/OAuth2 form.
6. **rate limiting per IP لا per account:** Redis اختياري، forwarded IP يحتاج policy واختبار spoof/NAT.
7. **backup غير مشفر:** gzip/tar وSHA-256 ليسا سرية؛ توثيق `docs/05-deployment/الأمان.md` يدعي AES-256 دون تنفيذ.
8. **fallback صامت:** أخطاء AI/audio/cache قد تتحول إلى نجاح طبيعي أو توصية قديمة.

لا يصح إعلان الامتثال أو “حذف جميع البيانات” أو “تشفير النسخ” من الوثائق وحدها.

## Critical Gaps

1. **نطاق المنتج مضلل** — Critical — الرؤية أوسع من capability الحالية؛ يلزم scope/versioning.

## Root Causes

- لا يوجد release gate واحد يجمع status، OpenAPI، CI، staging، artifacts، security، وacceptance.
- الرؤية والمتطلبات الأصلية لم تُversion ولم تُخفض صراحة إلى MVP/Planned/Future.
- الوثائق، code، smoke، Flutter models وschemas تطورت منفصلة بلا generated contract.
- وجود كود/اختبار اعتُبر دليلاً على الجودة أو التشغيل، دون نتيجة تنفيذ محفوظة.
- data lifecycle غير معرف من الجهاز إلى DB وAI provider وbackup.
- fallback catch-all استُخدم لتجنب فشل UX، لكنه أزال دلالة الخطأ.
- عدم وجود state machine للـdelivery/offline، أو idempotency على APIs ذات side effects.
- تراكم مسارات deployment والنسخ الاحتياطي دون canonical ownership.
- التركيز على structural integrity وmicrobench بدلاً من quality evaluation وload/recovery tests.
