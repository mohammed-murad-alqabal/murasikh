**تاريخ المراجعة:** 2026-09-13  
**المستودع المراجع:** `mohammed-murad-alqabal/murasikh`  
**الفرع والالتزام:** `main` عند الالتزام `389b39a`  
**نطاق المراجعة:** `docs/plans/todo-1.md` و`docs/plans/todo_2.md` مقابل الكود والبيانات والاختبارات وملفات النشر.

## الخلاصة التنفيذية

لم تُنفَّذ جميع البنود الواردة في الخطتين. المستودع يحتوي على **هيكل Backend أولي، وبيانات قرآن وأحاديث، وتصنيف موسع للحالات، وسكريبتات للاسترجاع الموزون، وملف Docker وملف CI**. لكن هذه العناصر لا تشكل تطبيقاً مكتملاً قابلاً للإطلاق؛ لأن مسار Flutter الأساسي غير موجود، والاسترجاع الموزون عبر Gemini غير مثبت كمخرج مكتمل أو مدمج بالطريقة المحددة في الخطة، وطبقات المصادقة وقاعدة البيانات والترحيلات وRedis والمراقبة غير مكتملة، كما أن الاختبارات لا تغطي معايير القبول.

**الحكم النهائي:** التنفيذ **جزئي**. لا يمكن اعتبار `todo-1` أو `todo_2` مكتملتين.

## أولاً: مراجعة `todo-1.md` — خطة MVP

### 1. الإعداد والبنية التحتية

| البند | الحالة | التقييم |
|---|---|---|
| مستودع Git | منفذ | المستودع موجود وله تاريخ commits منظم وفرع `main` |
| Docker | منفذ جزئياً | يوجد `docker/Dockerfile` و`docker-compose.yml` لتشغيل Backend فقط |
| PostgreSQL في Compose | غير منفذ | ملف Compose لا يشغل PostgreSQL |
| Redis في Compose | غير منفذ | ملف Compose لا يشغل Redis |
| Celery | غير منفذ | لا توجد تهيئة Celery أو مهام خلفية فعلية |
| Alembic | غير منفذ | لا يوجد مجلد `alembic` أو ملفات migrations |
| هيكل Backend المقترح | منفذ جزئياً | توجد بعض الحزم، لكن endpoints المصادقة والتوصية والتغذية الراجعة وفق الهيكل المقترح غير مكتملة أو مدمجة في ملفات مختلفة |

يوجد في `backend/app/main.py` مساران فعليان مهمان: `/api/v1/analyze` و`/api/v1/history`، إضافة إلى مسار تحليل الصوت. هذا لا يطابق المسار الموثق في الخطة والوثائق، وهو `/api/v1/recommend`. لذلك فإن أمر الاختبار المذكور في الخطة لا يستهدف المسار المنشور حالياً.

### 2. قاعدة البيانات والنماذج

نماذج SQLAlchemy الحالية تحتوي على `User` و`Verse` و`Hadith` و`Interaction` و`DelayedResponse` و`EmotionMapping`. هذا يمثل جزءاً مهماً من المخطط المقترح.

مع ذلك، توجد فجوات تمنع اعتبار طبقة البيانات مكتملة:

- لا يوجد نموذج `VerseEmotion` المطلوب في `todo_2.md`.
- لا توجد migrations لتطبيق الجداول على PostgreSQL.
- نموذج المستخدم موجود، لكن لا توجد طبقة مصادقة أو إنشاء رموز JWT مكتملة.
- نموذج `EmotionMapping` ما زال يحتوي على `example_hadiths` رغم أن خطة التحديث تطلب إزالة الأحاديث من قاعدة الاسترجاع.
- لا يوجد دليل على تشغيل PostgreSQL أو تطبيق المخطط في بيئة قابلة لإعادة البناء.

### 3. قاعدة المحتوى الشرعي

البيانات المحلية موجودة فعلاً:

- `backend/quran.json` يحوي 6236 آية عند عدّ الآيات داخل السور.
- ملفات الأحاديث الستة الموجودة تحوي إجمالاً 36227 حديثاً تقريباً.
- توجد سكريبتات `seed_quran.py` و`seed_hadiths.py` لإدخال البيانات إلى ChromaDB.

هذا يحقق وجود الأصول والبيانات، لكنه لا يثبت أن قاعدة ChromaDB التشغيلية مهيأة أو أن البيانات أُدخلت بنجاح في بيئة قابلة لإعادة الإنتاج؛ فمجلد `backend/chroma_db` ليس جزءاً مثبتاً في المستودع عند المراجعة، كما أن الاعتماديات اللازمة غير مثبتة في بيئة المراجعة.

### 4. RAG والاسترجاع الدلالي

يوجد `EmbeddingService` يستخدم نموذج `GATE-AraBERT-v1`، ويوجد `RAGEngine` لصياغة رد دافئ مع تعليمات تمنع اختلاق النص القرآني. كما أن نقطة التوصية الحالية تقيد الاسترجاع إلى الوثائق التي تحمل النوع `verse`.

لكن التنفيذ لا يطابق مواصفات خطة MVP كاملة للأسباب التالية:

- `EmbeddingService` يستخدم فهرس `verse_fingerprints.json` الموجود في الذاكرة لإعادة الترتيب، وليس metadata باسم `emotion_weights` الناتج عن سكريبت الخطة الجديدة.
- خدمة Redis موجودة كملف، لكن نقطة التوصية لا تستخدمها، ولا يوجد Redis في Compose.
- لا توجد آلية تحقق تشغيلية كاملة من المصدر والتفسير والرقم السُّوَري قبل إرسال النتيجة.
- خدمة `quran_service.py` تحتوي على دوال `pass` بدلاً من تنفيذ استرجاع فعلي.
- لا يمكن قياس زمن الاستجابة المستهدف، لأن اختبار الأداء غير موجود ولأن مسار التوصية يعتمد على تحميل النموذج وGemini دون اختبار تكاملي.

### 5. الاستجابة المدرجة

يوجد منطق جزئي للاستجابة المدرجة في `recommend.py`: الحالات الشديدة تحصل على رد فوري مختصر، وتُنشأ رسالة تفصيلية مؤجلة عبر `RAGEngine`. هذا يثبت وجود الفكرة الأساسية.

لكن لا توجد طبقة تأجيل فعلية تعتمد على Celery أو تخزين `delayed_responses` في قاعدة بيانات، ولا توجد اختبارات تثبت السلوك تحت الحالات المختلفة. لذلك يصنف هذا البند **منفذاً جزئياً**.

### 6. واجهة Flutter وOffline-First

هذا هو أكبر نقص في خطة MVP. مجلد `frontend` يحتوي على ملفات المنصات و`pubspec.yaml` واختبارات، لكنه لا يحتوي على `frontend/lib` إطلاقاً. وبذلك لا توجد ملفات التطبيق الأساسية مثل:

- `main.dart` وملفات التطبيق والمسارات.
- صفحات الإدخال والتوصية والإعدادات والتاريخ.
- خدمات API والتخزين والعمل دون اتصال.
- نماذج التوصيات وطبقة Repository وBLoC.
- شريط حالة عدم الاتصال أو منطق مزامنة التفاعلات.

وجود اختبارات تستورد `package:murassikh_app/...` لا يعوض غياب ملفات المصدر؛ بل يشير إلى أن الاختبارات كتبت قبل إكمال التطبيق أو أن المصدر غير موجود في الالتزام الحالي.

### 7. النشر وCI/CD

يوجد workflow واحد في `.github/workflows/ci.yml` يقوم بتثبيت الاعتماديات وتشغيل Flake8 وPytest. وجود الملف يحقق جزءاً من بند CI، لكن جودته لا تكفي للاعتماد عليه:

- خطوة الاختبارات تستخدم `python -m pytest || echo "No tests configured yet or tests failed"`، ولذلك قد تنجح المهمة حتى عند فشل الاختبارات.
- لا يوجد بناء Docker أو نشر أو دفع إلى Registry.
- لا توجد خدمات PostgreSQL أو Redis في workflow.
- لا توجد تغطية اختبارات أو رفع coverage كما ورد في الخطة.

## ثانياً: مراجعة `todo_2.md` — خطة الآية المثالية

### 1. العمر والجنس

Backend يدعم تمرير `user_context` اختيارياً، ويضيف العمر والجنس إلى Prompt محلل المشاعر في `emotion_analyzer.py`. هذا تنفيذ جزئي من جهة Backend فقط.

لم تُنفَّذ ملفات Flutter المطلوبة (`user_settings.dart` و`settings_service.dart` و`personal_info_screen.dart`) لأن `frontend/lib` غير موجود. لذلك لا توجد شاشة أو حفظ محلي أو اختبار لحقلي العمر والجنس.

**الحكم:** منفذ جزئياً في Backend، غير منفذ في التطبيق.

### 2. إزالة الأحاديث من قاعدة الاسترجاع

نقطة التوصية الحالية تستخدم:

```python
filters={"type": "verse"}
```

كما أن Prompt الصياغة يمنع ذكر الحديث. هذا يمنع نقطة التوصية الحالية من طلب وثائق الأحاديث إذا كانت metadata صحيحة.

لكن الخطة طلبت صراحة سكريبت `backend/scripts/purge_hadiths.py` لحذف وثائق الأحاديث من ChromaDB. هذا السكريبت غير موجود. كذلك ما زالت ملفات الأحاديث وسكريبت `seed_hadiths.py` موجودة، ووصف مجموعة ChromaDB في `embeddings.py` ما زال يقول: «القرآن والأحاديث والتفاسير». لذلك لا يوجد إثبات أن الأحاديث حُذفت من قاعدة الاسترجاع فعلياً.

**الحكم:** عزل جزئي في مسار التوصية، لكن مطلب الحذف والتنظيف غير منفذ أو غير مثبت.

### 3. قائمة الحالات الموسعة

يوجد `backend/app/core/taxonomy.py` ويحتوي على تصنيف واسع يزيد على 50 حالة، مع أبعاد إيمانية وسلوكية وموقفية ونفسية. هذا يحقق جوهر مطلب التوسعة.

لكن القائمة ليست مطابقة تماماً للقائمة الواردة في الخطة. فبعض الحالات المخططة مثل «شرك، نفاق، صدق، كذب، توكل، غرور، تواضع، استكبار، خشوع، إهمال، استهتار» لا تظهر كحالات مطابقة في الملف، بينما أضيفت حالات أخرى مثل «توحيد، يقين، حيرة، بصيرة، فقر، ديون، تعافي».

**الحكم:** منفذ جزئياً؛ التوسعة موجودة، لكن عقد القائمة المحدد في الخطة لم يُنفذ حرفياً.

### 4. توليد الأوزان عبر Gemini

يوجد `build_weighted_verse_index.py` ويحتوي على:

- تقسيم الآيات إلى دفعات.
- طلب أعلى سبع حالات لكل آية من Gemini.
- حفظ تقدم جزئي.
- محاولة تحديث metadata باسم `emotion_weights`.

لكن لا يوجد في المستودع `verse_weights_progress.json` أو `verse_weights_final.json` كناتج مكتمل. الملف الموجود `verse_fingerprints.json` يحوي 6236 مفتاحاً، لكنه ناتج عن سكريبت بصمات محلية يعتمد على تشابه embeddings، وليس دليلاً على نجاح عملية Gemini المحددة في الخطة.

كما أن سكريبت Gemini لا يعالج التقدم بأمان كامل عند الأخطاء؛ فهو يسجل أوزاناً فارغة عند خطأ JSON، وتعديل `b_idx` داخل حلقة `for` لا يعيد الدفعة فعلياً عند تجاوز الحصة.

**الحكم:** السكريبت موجود، لكن المخرج المكتمل والاعتماد التشغيلي غير مثبتين.

### 5. الاسترجاع الموزون

يوجد ترتيب هجين في `embeddings.py` يدمج درجة التشابه مع وزن الحالة من `verse_fingerprints.json`. هذا يحقق فكرة عامة قريبة من الاسترجاع الموزون.

لكن التنفيذ لا يطابق المطلوب في الخطة:

- لا توجد دالة `search_by_emotion_weighted`.
- لا توجد خوارزمية بحث متعدد الحالات كما وصفت الخطة.
- لا تُقرأ `emotion_weights` من metadata في ChromaDB.
- لا يوجد `VerseEmotion` في نموذج قاعدة البيانات.
- لا يوجد سياق عمر/جنس يدخل في حساب ترتيب الآيات؛ السياق يدخل فقط في Prompt تحليل المشاعر.

**الحكم:** منفذ جزئياً كترتيب هجين، وليس كتنفيذ كامل لخطة الاسترجاع الجديدة.

### 6. نقطة `/recommend`

التعديلات المفيدة موجودة في نقطة التوصية الحالية:

- استقبال `user_context`.
- تحليل المشاعر.
- تقييد الاسترجاع إلى القرآن.
- تمرير النتيجة إلى Gemini للصياغة.
- حفظ سجل التفاعل.

لكن المسار الفعلي هو `/api/v1/analyze` وليس `/api/v1/recommend`. كما أن محلل المشاعر يطلب حالة واحدة فقط، رغم أن خطة Smart Retrieval تتحدث عن احتمال إعادة أكثر من شعور. ولا توجد اختبارات API لهذا المسار تثبت أن الرد آية قرآنية فقط أو أن التنوع وعدم التكرار يعملان.

**الحكم:** منفذ جزئياً.

### 7. تحديث محلل المشاعر

تم تحديث Prompt ليستخدم التصنيف الموسع، وتمت إضافة fallback محلي لكلمات مفتاحية عديدة. مع ذلك، المخرجات محصورة في `emotion` و`confidence`، ولا توجد قائمة مشاعر متعددة أو أوزان لكل مشاعر كما تتطلب خوارزمية البحث المركب.

**الحكم:** منفذ جزئياً.

### 8. الاختبار والتثبيت على الجهاز

لم يتحقق هذا البند:

- لا توجد اختبارات للبحث الموزون.
- لا توجد اختبارات للتحقق من منع الأحاديث.
- لا توجد اختبارات لحقلي العمر والجنس.
- لا توجد اختبارات أداء أقل من ثانيتين.
- لا توجد اختبارات تنوع النتائج.
- لا يمكن تشغيل اختبارات Flutter لأن Flutter غير مثبت في بيئة المراجعة ومجلد `frontend/lib` مفقود.
- اختبارات Backend الحالية تختبر الجذر و`/health` فقط.

## الحكم النهائي

المشروع **ليس في حالة تنفيذ كامل للخطط**. الحالة الحالية أقرب إلى **نموذج Backend تجريبي مع أصول بيانات وسكريبتات بحث، وواجهة Flutter مفقودة، وتكامل إنتاجي غير مكتمل**.

يمكن اعتبار البنود التالية منجزة أو شبه منجزة: إنشاء المستودع، وجود ملفات Docker وCI، توفير بيانات القرآن والأحاديث، وجود نموذج GATE-AraBERT، إنشاء تصنيف موسع، ووجود مسار توصية يعتمد القرآن فقط في الاسترجاع الحالي.

ولا يمكن اعتبار البنود التالية منجزة: تطبيق Flutter وOffline-First، المصادقة والإنتاج الآمن، Redis وCelery وAlembic، حذف الأحاديث من ChromaDB، تنفيذ الأوزان الناتجة عن Gemini وربطها بالاسترجاع، اختبارات القبول والأداء، ومطابقة مسارات API مع الوثائق.
